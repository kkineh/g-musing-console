# 엔진 API 계약

콘솔(서비스팀)과 엔진(엔진팀) 사이의 유일한 접점. 이 문서에 적힌 것만 지키면
엔진 내부 구현은 콘솔이 몰라도 된다 — 프롬프트를 어떻게 구성하든, Claude Agent SDK를
어떻게 부르든, 지식베이스를 어떻게 참조하든.

콘솔 쪽 구현은 `src/lib/engine.ts` 한 파일에만 있다.

## 전제

- 되묻기는 musing의 주요 기능이다. 한 번 묻고 끝나는 구조가 아니다.
- 되묻기는 두 층위로 나뉜다. 아래 "되묻기" 절 참고.
- 콘솔은 대화(chat)와 턴(turn)을 저장하고, 엔진은 세션을 들고 있다.

## 엔드포인트

### `POST /process`

새 대화를 시작하거나, 기존 대화를 이어간다.

**요청**

```jsonc
{
  "type": "LOGIC_REVIEW",   // LOGIC_REVIEW | ERROR_CAUSE
  "memberId": "gist-v2",
  "question": "...",

  // 이어가기일 때만. 첫 턴에는 없다.
  "sessionId": "5b3f2c1a-...",

  // 되묻기에 답할 때만. 아래 "되묻기" 절 참고.
  "answers": {
    "어느 화면에서 조회한 결과인가요?": "개인별 명세"
  }
}
```

**응답 — 완료**

```jsonc
{
  "status": "done",
  "sessionId": "5b3f2c1a-...",   // 항상 반환. 콘솔이 저장해 다음 턴에 보낸다.
  "answer": "지급규정 개정이 원인입니다. ...",
  "references": [
    { "locator": "PKG_SU_CALC:412", "description": "합산 기준 분기" }
  ],
  "trace": [
    { "label": "유형 판별", "detail": "로직 확인", "elapsedMs": 400 }
  ],
  "usage": { "elapsedMs": 107000, "tokens": 38200, "filesRead": 7, "dbQueries": 4 }
}
```

**응답 — 되물음**

```jsonc
{
  "status": "waiting_input",
  "sessionId": "5b3f2c1a-...",
  "questions": [
    {
      "question": "어느 화면에서 조회한 결과인가요?",
      "header": "조회 화면",
      "options": [
        { "label": "지사 소계", "description": "지사 단위로 합산한 화면" },
        { "label": "개인별 명세", "description": "설계사 단위 내역 화면" }
      ],
      "multiSelect": false
    }
  ],
  "trace": [ /* 되묻기 전까지의 단계 */ ]
}
```

**응답 — 실패**

```jsonc
{
  "status": "failed",
  "sessionId": "5b3f2c1a-...",   // 있으면 반환
  "error": "저장소 사본 최신화 실패: ..."
}
```

## 되묻기

두 층위가 있고, **계약상으로는 똑같이 `waiting_input`으로 표현된다.**
콘솔은 둘을 구분할 필요가 없다.

### (1) 실행 중 되묻기 — `AskUserQuestion`

에이전트가 처리 도중 판단이 필요해 되묻는 경우. 요청에 조회 기준이나 대상
식별 정보가 없어서 스스로 유추하면 위험한 지점.

Agent SDK에서는 `canUseTool` 콜백이 발화하고 실행이 멈춘 채 대기한다.
**콜백이 답을 돌려줄 때까지 `query()`는 끝나지 않는다.**

웹 서비스에서는 이게 문제다 — 사용자가 몇 분씩 답을 안 할 수 있는데 그동안
HTTP 요청과 프로세스를 붙잡고 있을 수 없다. SDK는 이 경우를 위해
`PreToolUse` 훅의 `defer` 결정을 제공한다: 프로세스를 종료하고 나중에
세션에서 재개한다.

**엔진팀이 정할 것**: 되묻기가 걸렸을 때 프로세스를 붙잡을지(`canUseTool` 대기),
`defer`로 끊고 나중에 재개할지. 콘솔은 어느 쪽이든 `waiting_input` 응답만 받으면 된다.

### (2) 실행 후 되묻기 — 세션 재개

턴이 완료된 뒤 사용자가 추가 질문을 하는 경우. 콘솔이 저장해둔 `sessionId`를
그대로 보내면 엔진이 `resume`으로 이어간다.

## 세션의 수명

Agent SDK 세션은 **파일로 남는다**: `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`.
여기서 두 가지 제약이 생긴다.

1. **같은 머신에서만 재개된다.** 엔진 서버를 여러 대로 늘리면 요청이 다른 서버로
   가는 순간 재개가 깨진다. 로드밸런서에서 세션 고정을 하거나,
   `sessionStore` 어댑터로 외부 저장소에 미러링해야 한다.
2. **컨테이너를 재시작하면 사라진다.** 디스크가 휘발성이면 이어가기가 안 된다.

**엔진팀과 합의할 것**: 위 둘을 어떻게 다룰지. 콘솔은 `sessionId`를 저장하고
돌려줄 뿐, 그게 실제로 살아있는지는 보장할 수 없다.

**콘솔 쪽 대비**: 재개가 실패하면 엔진이 `failed`로 응답하고, 콘솔은
"이 대화는 이어갈 수 없습니다. 새 대화로 시작해주세요"를 보여준다.

## 타임아웃

한 턴이 1~2분 걸린다. 되묻기가 걸리면 사용자 응답 시간만큼 더 길어진다.

- 콘솔 → 엔진 HTTP 타임아웃: 5분 (되묻기 응답은 그 전에 와야 한다)
- 되묻기 대기는 타임아웃에 포함하지 않는다 — `waiting_input`으로 일단 응답을
  돌려주고, 사용자 답이 오면 새 요청으로 보낸다

## 권한 경계

엔진이 지켜야 한다. 지금 범위는 읽기만 필요하다.

| 대상 | 허용 |
| --- | --- |
| 회원사 저장소 | 읽기 전용 |
| 회원사 DB | 조회 전용 (DML 미실행) |

쓰기 권한은 필요해지는 시점에 열고, 그때 이 표를 고친다.

## 엔진팀이 채울 것 (2026-09-28 회의)

위 요청 필드는 콘솔이 지금 보내고 있는 것이다. 엔진이 Claude Agent SDK를 돌리는 데
이것으로 충분한지, 모자라면 무엇이 더 필요한지는 엔진팀이 정한다.

- [ ] 이 필드로 충분한가. 모자라면 무엇이 더 필요한가
- [ ] `type`을 엔진이 쓰는가, 아니면 질문만 보고 스스로 판단하는가
- [ ] `memberId`로 저장소·DB를 어떻게 찾는가 (엔진이 매핑을 들고 있는지)
- [ ] 되묻기를 선택지(`options`)로 주는 게 맞는가, 자유 입력이 필요한 경우가 있는가
- [ ] `references`의 `locator` 형식 — 파일 경로인지, 패키지:라인인지, 섞이는지

## 아직 안 정한 것

- 인증 방식 (지금은 없음. 사내망 전제)
- 동시 실행 제한 — 저장소 사본 충돌 때문에 큐가 1개인데, 되묻기로 턴이 길어지면
  큐가 막힌다. 되묻기 대기 중인 턴은 큐에서 빼야 할 것 같은데 엔진팀과 논의 필요
- 취소 (사용자가 처리 중단)
